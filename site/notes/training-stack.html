训练链路

从机房到一次参数更新。五层东西各自决定一件事，任何一层出问题，最后都表现为「训练很慢」。

2026-11-03约 8 分钟训练全系列 ›

开始接触训练之后最容易犯的错，是把「慢」当成一个整体去治。实际上它至少有五个来源，而排障的第一步是判断卡在哪一层。

范围。以单机到中等规模训练为主，用之前那套 LingBot-VLA 的配置做贯穿例子。不涉及 MoE 路由的分布式实现细节，也不给具体框架的调参配方。

1. 五层，各管一件事

层它决定什么出问题的表现
基建能不能跑完跑到一半挂、数据喂不上
平台跑得稳不稳重启丢进度、多机不同步
算子跑多快GPU 利用率上不去、显存炸
模型装不装得下OOM、只能开 batch=1
优化器更新得好不好loss 不降、发散、显存比预期大

这五层不是并列的，是依赖的：算子的效率取决于模型的结构，模型的显存取决于优化器的状态，而这一切都要在基建上跑得完、在平台上不掉链子。

2. 基建：训练首先是个可靠性问题

先说一个容易被忽略的算术：假设单卡平均无故障时间是一万小时，一千张卡跑三天——

1000 卡 × 72 小时 ÷ 10000 小时 ≈ 7.2 次故障

也就是说，一次完整的训练必然会被打断好几次。所以集群设计的第一优先级不是峰值算力，而是能恢复：checkpoint 周期要短于故障间隔，重启要能自动续训。

三条硬件事实决定了后面的所有选择：

一、卡内互连。同一台机器里 GPU 之间的带宽（NVLink 通常几百 GB/s）远高于跨机网络（IB 通常几十到几百 Gb/s，换算成字节还要除以 8）。通信密集的并行方式只能放在机器内部——这是张量并行的部署边界。

二、显存墙。80 GB 是现在的主流上限。下一节会把账算给你看，为什么 6B 以上的模型必须切分。

三、存储带宽。如果数据集在远端，每张卡每秒要喂几百 MB 到几 GB 的样本。当 dataloader 成为瓶颈时，GPU 利用率会掉到个位数——而且监控上看起来「GPU 在等」。

常见的存储分层：本地 NVMe 缓存 → 节点级共享 → 远端对象存储。训练时先把数据拉到本地，是最便宜的加速手段之一。

3. 显存账：四份开销

训练一个模型，显存里至少躺着四样东西，缺一不可：

项是什么典型字节/参数
权重当前参数值fp32: 4 · bf16: 2
梯度反向传播算出的 ∂L/∂wfp32: 4 · bf16: 2
主权重副本混合精度下保留的 fp32 版本，更新用它混合精度: 4 · 纯 fp32: 0

加起来，AdamW + 混合精度正好是 16 字节/参数——这个数字值得记住，很多容量估算可以直接心算。

这个计算器立刻给出两个直觉：

一、优化器状态是最大的一块。AdamW 每参数 8 字节，比权重本身还大。这也是为什么「换个省显存的优化器」是常见手段——Muon 只存动量，直接省掉 4 字节/参数。

二、70B 模型单卡绝无可能。16 字节乘 70B 是 1120 GB，十几张 80G 卡才放得下模型状态。这就是并行不是可选项、而是必选项的原因。

4. 并行：切什么，切在哪

显存放不下时，有四把刀，切的维度不同。

方式切什么通信量放哪
数据并行 DP批次每步一次梯度 all-reduce跨机也行
ZeRO / FSDP把 DP 的状态再切开比 DP 多，换显存跨机也行
张量并行 TP单层内部的矩阵每层两次 all-reduce只能机内
流水并行 PP按层切成若干段段间传激活跨机也行

选择的顺序通常是：

先 ZeRO/FSDP，因为它改动最小、收益直接——把优化器状态和梯度按数据并行度切开，显存立刻降。

再考虑 TP，但要记住它的通信量随层数线性增长，因此被限制在机内。常见做法是把 TP 设为单机 GPU 数（比如 8）。

PP 用来跨越单机边界，把层分到不同机器上。代价是流水线气泡：前后段要等，利用率下降。

三者叠起来就是所谓的 3D 并行。经验配比通常是「TP 打满单机、PP 尽量小、剩下的全给 DP」。

5. 算子：钱到底花在哪

一次前向反向里，绝大多数浮点运算发生在矩阵乘上。所以「算子优化」听起来像一个很宽的话题，实际上九成时间在回答两个问题：GEMM 的效率，以及注意力那 O(S²) 的部分。

GEMM。全连接层、QKV 投影、输出投影，全是矩阵乘。BLAS 库已经把它优化到接近硬件峰值，所以你能做的是「让它更大、更规整」——批量越大、维度越整齐，效率越高。

注意力。分数矩阵是 S×S，序列翻倍，这一项翻四倍。长序列下它会超过 GEMM 成为瓶颈。flash attention 的收益不在算术，而在不把 S×S 矩阵写回显存——省的是带宽和显存，这一点和 softmax 的在线写法是同一个思路。

融合。LayerNorm、GELU、残差相加这些逐元素算子单独看都很便宜，但它们各自都要读写一遍完整的激活张量。把它们合进一个 kernel，省下的带宽往往比优化矩阵乘更可观。

判断「算子层有没有问题」的指标是 MFU（模型浮点利用率）：实测 FLOPs 除以硬件峰值。训练良好的大模型通常在 35%–50%；低于 20% 基本说明有地方在等。

6. 优化器：更新规则和它的额外开销

上一节算过显存，这里说它对训练质量的影响。

优化器状态特点什么时候用
SGD + momentum1 份最省，对超参敏感CV 经典配方
AdamW2 份稳、好调，默认选择绝大多数任务
Muon1 份正交化更新，收敛快大规模预训练

几个容易踩的点：

混合精度下的数值稳定。梯度要累加在 fp32 里，更新也在 fp32 里做，再把结果转回 bf16。这就是「主权重副本」存在的原因——没有它，小梯度会被 bf16 直接吃掉。

学习率与批量的耦合。有效批量变大时，学习率通常要跟着放大（线性或平方根规则），否则收敛变慢。这条在换并行策略、改梯度累积步数时特别容易忘。

换优化器不能只换名字。Muon 的学习率语义和 AdamW 不同，权重衰减也要重新标定——这在 优化器那篇里展开过。

7. 平台：一个 step 的编排

把上面几层串起来，一次训练步是这样一个循环：

取批次 → 拷到显存 → 前向 → 反向 → 梯度同步 → 优化器更新 → 记录 → 存 checkpoint

每一步都可能成为瓶颈，而且它们的表现完全不同：

环节卡住时的表现先看什么
取批次GPU 利用率周期性掉到个位数dataloader 的 worker 数与存储带宽
H2D 拷贝利用率不满但也不空是否用了 pinned memory、是否异步
前向反向利用率高但步时长算子效率、MFU
梯度同步多卡时步时长随卡数上升通信带宽、是否与反向重叠
优化器更新固定开销，占比随模型增大是否用了 fused optimizer

「梯度同步与反向重叠」值得单独提：现代框架会在反向传播算到某一层时就开始同步那一层的梯度，而不是等全部算完再统一 all-reduce。没有这个重叠，多卡训练的加速比会明显打折。

8. 回到 LingBot：把这条链跑一遍

用之前那套配置检验一下，看五层是怎么对上的。

层这套配置里的实际情况
基建单卡 A800 80 GB；数据在本地，不存在远端拉取；没有多机，所以没有故障恢复压力
平台微批次 1、梯度累积 4，有效批量 4；每 100 步存一次检查点
算子flow matching 十个积分步，每步一次前向；动作专家是 MoE，32 个专家选 4 个
模型6B 总参数，但主干（Qwen3-VL-4B）冻结，只训动作专家
优化器Muon，只存动量，比 AdamW 省 4 字节/参数

这里有一个容易算错的地方：冻结主干会大幅降低显存里「状态」的部分。16 字节/参数那条规则只适用于「全部参数都训练」；冻结的部分只有权重（2 字节），不需要梯度、主副本和优化器状态。

所以「6B × 16 B/参数 = 96 GB」这个心算，在这套配置下是错的——真正训练的只是其中一小块。这也解释了为什么单卡 80G 能跑起来。

另一件事：微批次 1 + 有效批量 4，意味着 1000 次优化器更新只看了 4000 个样本。按之前算过的覆盖率，大约五分之一个 epoch。所以那轮结果不能用来判断「模型能不能学会」，只能判断「管线通不通」。

至于每步 9.1 秒里各环节占多少——这必须实测，不能猜。一个便宜的判断方法：把 dataloader 换成一个返回固定张量的假加载器，如果步时长明显下降，瓶颈就在数据侧。

9. 症状 → 层级

排障时先定位到层，再谈具体手段。

症状大概率在哪层下一步
GPU 利用率周期性归零基建 / 平台看 dataloader 与存储带宽
利用率高但步时长长算子算 MFU，看是 GEMM 还是 attention
OOM，且只在加大 batch 时出现模型 / 激活梯度检查点、减小序列
OOM，一开始就出现优化器状态用 ZeRO 切状态
loss 不动或发散优化器 / 数据先查学习率与 warmup，再查标注
多卡比单卡还慢并行策略看通信是否重叠、TP 是否跨机
重启后 loss 跳变平台检查点是否包含优化器状态与数据进度

10. 收尾

五层链路里，越往下越是「物理约束」，越往上越是「工程选择」：

基建给你多少带宽、多少显存，是硬的；算子的效率由硬件和库决定，也很难突破；而模型结构、优化器、并行策略是你可以反复权衡的。

所以真正有效的优化顺序通常是从上往下：先看数据喂不喂得上，再看并行切得对不对，最后才是算子微调。反过来做，很容易在 5% 的提升上花掉一周，而真正的瓶颈还躺在 dataloader 里。
