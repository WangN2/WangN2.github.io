1. 目标与真实场景

我们要实现的，不是让大模型直接计算轮速，而是让轮臂式 G2 接受“探索工位、建立地图，最后导航到上料架”的任务，能够自主选择观察位置、发起规划、读取运动反馈并诊断失败。工作区域按约 5×10 m 的仪表线束工位考虑：多工位、窄通道、频繁移动、经常需要精确对位。

本文是技术方案，不是已经完成的 G2 真机测评。SDK 接口、传感器频率、碰撞包络、定位误差都必须以当前设备的实际数据验证。下文所有坐标均为格式示例。

2. 架构：Astra 决策、SLAM 建图、导航执行

任务 → Astra（语义理解／探索策略／失败归因）
↓ 结构化工具申请
Robot Navigation Harness（校验／授权／状态机／日志）
↓ SDK Bridge / ROS 2
SLAM（地图与定位）＋ Navigation（规划与避障）
↓ 受控运动指令
G2 底盘控制与独立安全保护 → 传感器反馈
模块职责不做什么
Astra任务拆解、选择探索目标、异常恢复策略不直接控制速度或绕过安全互锁
Harness工具合同、状态检查、授权、日志不把语言输出当执行证据
SLAM传感器匹配、里程计、位姿图优化与地图不交给 LLM 直接估计精确位姿
Navigation全局路径、局部避障、控制闭环不等待云端模型处理紧急制动
G2 Controller运动执行、故障和急停保护不允许 Agent 越权关闭保护

核心原则是高层低频决策和低层高频控制分离。Astra 可以换模型，但机器人仍应可独立安全停车。

3. 技术路线：原生导航还是 slam_toolbox + Nav2

首选复用 G2 当前固件开放的建图、定位和导航功能，减少软件栈与硬件耦合。若有原生 SLAM 和位姿但导航能力不足，可适配 ROS 2 Nav2；若只开放雷达、里程计与底盘控制，才考虑自己集成 slam_toolbox + Nav2。不能将其他机型 SDK 话题当成 G2 已存在的接口。

已具备建议仍需确认
原生 SLAM + 导航SDK Tool Adapter仅规划、取消、状态回调
原生 SLAM + 位姿接 Nav2地图、TF、底盘指令协议
雷达 + Odom + TFslam_toolbox + Nav2传感器标定、控制开放程度

为调试可复现性，优先把原生 SDK 封装成等价工具协议，而不是改造机器人核心控制器。

4. 第一步：探测 G2 SDK 与 ROS 2 接口

先做只读诊断，记录 topic、service、action、frame、消息类型、频率和时间戳。

printenv ROS_DISTRO
ros2 node list
ros2 topic list -t | grep -Ei 'map|scan|lidar|points|odom|pose|tf|costmap|path'
ros2 action list -t
ros2 service list -t | grep -Ei 'map|slam|localiz|nav|plan'
ros2 run tf2_ros tf2_echo map base_link
ros2 topic info /map -v
ros2 topic echo /odom --once

如果 G2 当前使用厂家私有通信栈、ROS 2 Bridge 未启动或 frame 命名不同，上述命令可能失败；这不是没有导航功能的证据。需要转查官方 GDK SDK。尤其要确认 map→odom→base_link 的可用性和坐标/时间一致性。

5. Astra 的工具协议：只读、仅规划、执行严格分权

拟封装工具作用权限
robot_get_state位姿、控制模式、健康状态只读
robot_observe图像、激光与障碍摘要只读
map_start / map_save管理 SLAM 生命周期受控
frontier_get_candidates可达前沿与收益评估只读
navigation_plan仅规划、无运动只规划
navigation_execute执行有效 plan_id显式授权
navigation_get_status进度和失败原因只读
navigation_cancel取消并核实停止本地紧急通道
{
  "tool": "navigation_plan",
  "arguments": {
    "goal": {"frame": "map", "x": 2.4, "y": 1.3, "yaw": 1.57},
    "map_version": "map_008",
    "footprint_mode": "tray_loaded"
  }
}

以上名称由项目自行定义，绝非已确认存在的 G2 SDK API。建议计划结果包含 plan_id、request_id、map_version、robot_state_hash、expires_at、feasibility。坐标/地图版本、碰撞包络或定位状态变化时，旧计划必须失效。尤其避免“仅规划调用实际就执行”的耦合。

6. 自主建图：Frontier Exploration 与 Astra 的协作

Frontier 是占据栅格地图上已知自由区与未知区的边界。首先由确定性算法提取、聚类并生成安全观测目标，再由规划器评估可达性，最后 Astra 对候选区域进行任务级排序。可以使用下面的启发式评分，但它不是执行安全证书。

score = α × information_gain − β × travel_cost − γ × risk − δ × revisit_penalty
while task_active:
    state = robot_get_state()
    if state.localization_lost or state.safety_stop:
        enter_safe_hold(); break
    frontiers = frontier_get_candidates()
    options = [f for f in frontiers if f.reachable and f.clearance_ok]
    if not options:
        finish_or_request_review(); break
    target = astra_choose(options, mission_context)
    plan = navigation_plan(target)
    if plan.valid and execution_policy_approves(plan):
        result = navigation_execute(plan.id)
        record_feedback(result)
    else:
        record_rejection(plan)
    refresh_map_and_frontiers()

探索的完成不应以模型一句“地图完成了”为准。要结合可达覆盖率、剩余有价值前沿、回环后地图稳定性、定位质量和人工标定的禁入区域。对狭窄工位，严禁为了提高未知格覆盖率盲目探入设备之间。

7. 语义地图：把“上料架”落到 map 坐标

occupancy grid 表示哪里有障碍，Semantic Map 则补上工位类别、工艺语义、可接近方位、对位方式和校准来源。语义观测必须经过视觉几何估计、TF 变换和物理校验后才能写入世界坐标，不让模型凭图像直接猜出厘米级位置。

stations:
  loading_rack:
    type: material_supply
    frame_id: map
    approach_pose: [1.2, 2.4, 1.57]  # 示例
    docking: visual_refinement
  harness_board:
    type: assembly_station
    frame_id: map
    approach_pose: [3.1, 1.8, 0.0]

可设置“导航到工位前方安全等待点”与“视觉伺服精准对位”两个阶段：前者适合 Nav2，后者适合 AprilTag 或厂家精确停靠接口。地图更新后需要重新验证所有站点坐标与可达性。

8. 轮臂式机器人：底盘路径不是全身安全

手臂收拢与伸出、夹爪外形、携带上料盘时的外伸、线束柔性摆动，都可能使可通行空间发生变化。至少定义 stowed、tray_loaded、station_docking 三种碰撞和速度模式。规划结果与相应模式绑定；模式改变后必须重新规划。

2D footprint 和 inflation layer 不等于全身 3D 碰撞检查。工位横梁、桌面突出部分和悬空线束尤其需要三维感知或现场禁行规则。先用固定收臂姿态实现稳健移动，再推进 Whole-Body Planning，避免一开始同时引入太多未验证变量。

9. 任务状态机与故障恢复

IDLE → OBSERVE → MAP/LOCALIZE → SELECT → PLAN_ONLY
→ VALIDATE → EXECUTE → VERIFY → LOG → NEXT
任何关键异常 → SAFE_HOLD / HUMAN_REVIEW
故障系统动作
定位丢失、TF 时序异常进入安全停止，检查传感器和重新定位
路径规划失败给前沿点标记失败，选择其他目标
局部通道受阻局部避障、有限次数重规划，随后等待/接管
Astra 请求超时底层安全策略独立生效；不得因等待云端推理继续冒险运动
状态/包络变化废弃旧 plan_id，重新规划和审批

完成条件由导航 action 结果、位置与朝向误差、稳定停车反馈等证据共同判断。人的任务授权、Agent 的 API 权限、软件执行许可和控制器安全互锁不是一种授权，任何一层都不应伪造另一层状态。

10. 工程拆分与日志设计

g2_navigation_agent/
├── agent/          # Astra client / prompt / tool schema
├── harness/        # permissions / state machine / event log
├── g2_bridge/      # GDK adapter / ROS 2 action clients
├── mapping/        # frontier / map metrics / semantic map
├── navigation/     # plan-only / execution / monitor
├── config/         # station poses / footprint modes
└── tests/          # offline / sim / fault injection

日志必须记录 task_id、request_id、model_version、sdk_version、map_version、robot_pose、tool_call、validator_decision、execution_state、feedback。分别标注“生成计划”“验证通过”“命令已下发”“机器人实际运动”“导航任务成功”，绝不互相替代。对于先前碰到的 G2 执行准入问题，这套证据链也是最短排查路径。

11. 分期实施和验收

阶段做什么验收
P0 接口摸底只读 SDK、ROS 2、TF 和地图接口表和时间戳一致性
P1 仿真闭环Frontier → plan → simulated execution覆盖率、重试与错误恢复统计
P2 低速受控真机限定区域自主探索停止验证、导航日志、人工接管可用
P3 工位导航固定站点往返和靠近任务成功率、停靠误差及碰撞/近失记录
P4 语义导航自然语言选站、地图与失败记忆语义目标准确率和独立到达验证

建议以地图覆盖率、定位漂移、路径长度/理论最短路径、平均规划耗时、到达率、人工接管率、错误停机、近失事件和恢复成功率作为指标。验收阈值需依据真机数据和风险评估共同确定，而不是凭空承诺厘米级精度。

12. 下一步：从接口清单开始，而不是继续堆 Prompt

最短路径是：确认 G2 当前开放的 SLAM/导航能力 → 实现 get_state + plan_only + execute + status → 仿真 Frontier 闭环 → 人工监督的低速探索 → 语义工位与精停。只有确认实际 GDK API 名称和能力以后，才可以把抽象接口替换成真机调用。

结论：Astra 适合做有证据约束的导航 Agent，不适合替代 SLAM 后端、实时局部规划或设备安全系统。将“模型提议、Harness 验证、导航执行、证据反馈”变成稳定协议，是线束机器人走向自主作业的关键。
