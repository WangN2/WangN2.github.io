nvJPEG
是怎么快起来的

JPEG 解码里有一半天生串行。nvJPEG 没有让那一半变快——它让那一半，和另外一半同时进行。

1. 真正的难处：不是慢，是串行

很多人以为 JPEG 解码慢是因为计算量大。不是。它慢，是因为有一部分工作没法并行。

解码拆开是五步：

阶段做什么能不能并行
熵解码比特流 → DCT 系数的整数几乎不能
反量化系数乘回量化表能，完全独立
反余弦变换每个 8×8 块变回像素能，块与块无关
色度上采样把缩小的 Cb/Cr 放大能
色彩转换YCbCr → RGB能，逐像素

为什么第一段不能并行？两个原因。

一是变长编码。Huffman 码字没有固定长度，你不解完前一个符号，就不知道下一个比特从哪里开始。这是一条纯粹的前缀依赖链。

二是直流系数的差分预测。JPEG 里每个块的直流系数不是独立存的，而是存「和前一个块的差值」。所以块 N 的直流值依赖块 N-1，一路链下去。

这条链有一个例外：重启间隔。编码器每隔若干块插入一个重启标记，把预测器清零。有了它，一条流就可以切成几段独立解码。这也解释了为什么某些 GPU 路径会明确要求「无重启间隔」，而另一些恰好能利用它。

于是问题清楚了：后面四步占了绝大部分计算量，却全卡在第一步上。

2. 切分：把串行的留在 CPU

nvJPEG 的答案很直接：既然第一步串行，就让它留在 CPU；后面四步是纯并行的像素运算，交给 GPU。

CPU：熵解码 → DCT 系数
　　　↓　页锁定内存，异步拷贝
GPU：反量化 → 反余弦 → 上采样 → 色彩转换 → RGB（直接落在显存）

这个切法有两个关键结果。

第一，结果不用回来了。传统做法是 CPU 解完得到一张 RGB 图放在主机内存，再整体拷到显存——那是一次几 MB 的传输。现在像素直接在显存里生成，那一趟省掉了。

第二，两段可以同时跑。CPU 在解第 N+1 张的比特流时，GPU 正在算第 N 张的反变换。这才是整套设计真正的收益来源——不是某一段变快了，是两段叠在一起了。

注意中间那一跳搬的是系数，不是像素。系数的体积和一帧 RGB 在同一量级，所以这一跳并没有被消灭，只是被掩盖在计算后面。

3. 为什么内存要特殊处理

上面那句「异步拷贝」听起来轻松，前提是那块主机内存必须是页锁定的。

普通 malloc 出来的页可能被操作系统换到磁盘。为了安全，CUDA 在拷贝时必须先把页锁住、拷完再解锁——这个开销让传输慢一个数量级，而且无法真正异步。

所以 nvJPEG 让调用方显式创建页锁定缓冲，并把它挂在解码状态上。库内部所有主机侧的中间结果都放这里：熵解码出来的系数，以及某些路径下的临时数据。

同理，显存侧也有一块由调用方提供的设备缓冲。这两块缓冲加一个解码状态，就构成了 nvJPEG 里那个「解码器」的实际内存模型。

这也解释了一个常见现象：同样的代码，换成普通内存就慢一半，而且不报错。

4. 三种后端，其实是三种流水线架构

后端不是一个调优参数，它选择的是这条流水线怎么组织。

后端CPU 做什么GPU 做什么本质
HYBRID熵解码反变换与色彩转换两段流水线
GPU_HYBRID只有解析熵解码也上 GPU三段都进 GPU
HARDWARE无无整条固化进固定功能单元

第二种值得多说一句。GPU 做 Huffman 是出了名的低效——这是图形学界的老结论。nvJPEG 只在批量足够大时才启用它（文档里的阈值是 50 张），因为批量小的时候，GPU 熵解码的额外开销反而盖过收益。

第三种是另一条路。Ampere 之后，A100 这类卡上有一颗 NVJPG 单元，把整个解码流程做成硬件电路。它不跑 kernel，也就没有启动开销，吞吐最高。代价是能力被裁死：只支持 baseline、单 scan、1 或 3 通道，不支持 4:1:1 和 4:1:0 采样。

所以选后端这件事，本质是问：你的数据流长什么样，配得上哪条流水线。

5. 分阶段 API：让重叠真正发生

如果只调一个 nvjpegDecode()，库内部会帮你把三段串起来跑——但你没法让第 N+1 张的熵解码和第 N 张的计算重叠，因为接口是阻塞语义的。

要重叠，就得把三段拆开。这就是「分阶段 API」存在的全部理由：

nvjpegDecodeJpegHost()　　　　　　→　熵解码，产出系数
nvjpegDecodeJpegTransferToDevice()　→　系数送显存
nvjpegDecodeJpegDevice()　　　　　→　反变换与色彩转换

拆开之后，三段就是三个可以各自排队的资源：CPU、PCIe、GPU。它们能同时对不同的图片工作。

6. 重叠之后，谁说了算

把时间线拉长看，会发现一件有意思的事：重叠并不能让总时间无限变短。

流水线的吞吐由最慢的那一段决定。六张图、三段等长的时候，理想总时长是「一段的长度 × 6 加上填充」，而不是「三段之和 × 6」。加速比的上限就是三段之和除以最慢那段——在默认参数下大概两倍。

拖动上面的滑块就能看到瓶颈转移：把 GPU 时间拉到最长，整条线被 GPU 卡住，CPU 早早解完无事可做；反过来压短 GPU，瓶颈就跑到 CPU 那边去。

这也解释了为什么批量小时收益会消失：流水线要「灌满」才有重叠。只解一两张图，填充和排空的时间占比太高，串行反而更简单。

7. 编码：把流水线反过来走

编码是同一套结构的逆序：色彩转换（RGB → YCbCr）、色度下采样、正余弦变换、量化、熵编码。

对应地，CPU 在编码路径上做的事变成了熵编码，GPU 做前面的像素变换。同样的分工理由：熵编码也是变长、有依赖的串行过程。

有意思的是转码。如果你只是想改元数据、换个容器，并不需要重算一遍余弦变换——库提供了直接搬运量化表与元数据的接口，让系数原封不动地重新打包。

这才是「无损转码」这个词的准确含义：不是解压再压，是绕过反变换和正变换，直接搬系数。一旦经过一次完整的解码再编码，量化的损失就叠加了两次。

8. 收尾：它换的是流水线，不是算法

回头看，nvJPEG 没有发明新的解码算法。它只做了三件事：

把串行的部分留在它擅长的处理器上；把并行的部分交给更擅长的处理器；再用分阶段的接口，让两半同时进行。

所以它不是「更快的 libjpeg-turbo」。它是同一条算法，换了一种组织方式。

这句话反过来也成立：如果你的数据量根本喂不饱这条流水线，组织方式再好也没有收益——那时候 CPU 就该老老实实干活。
