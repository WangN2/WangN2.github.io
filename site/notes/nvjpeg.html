1. 它是什么，不是什么

nvJPEG 是 CUDA Toolkit 里那个用 GPU 做 JPEG 编解码的库，`libnvjpeg`。

它的诞生场景很具体：深度学习的数据加载，和超大规模图像服务。这两个场景的共同点是——一次要处理成千上万张图，而 JPEG 解码在 CPU 上实实在在是个瓶颈。

三个容易混淆的邻居，先分清：

库管什么
nvJPEG静态图 JPEG 的编、解码与转码
NVDEC / NVENC视频流：H.264、H.265、AV1
nvJPEG2000 / JPEG-LS医疗、遥感那类无损与近无损格式

所以别指望用它解视频流——那是另一个库，接法完全不同。

2. 它快在哪

一句话：把能并行的部分搬到 GPU，把不能并行的部分留在 CPU。

JPEG 解码里，Huffman 熵解码天生串行——你不解完前一个符号，就不知道下一个比特在哪。这活儿 GPU 干得很差。而反量化、反余弦变换、上采样、色彩转换是像素级并行，GPU 的强项。

所以经典形态是混合解码：CPU 出 DCT 系数，通过 pinned 内存异步送到显存，GPU 做剩下的，结果直接落在显存里。省掉的不只是解码时间，还有「解完再从主机拷一次」的那趟传输。

这一段的原理细节在上一篇，这里只记住一个结论：它加速的是「解到哪、在哪解」，不改变「解出来是什么」。

3. 三种后端

nvJPEG 不是一个解码器，是一组解码器。选哪个由 `nvjpegBackend_t` 决定。

后端熵解码在哪什么时候用限制
`HYBRID`CPU兜底，什么都能解大批量时 CPU 就是瓶颈
`GPU_HYBRID`GPU大批量 baseline，想把 CPU 也省下来文档里 GPU 熵解码的切换点是批量 > 50
`HARDWARE`固定功能单元吞吐最高，A100 之后才有只吃 baseline、单 scan、1 或 3 通道

还有个容易被忽略的变体：带 `_DEVICE` 后缀的版本允许比特流直接在显存里，连那次 H2D 传输都省了。适用于「上游本来就在 GPU 上产图」的链路，比如合成数据。

另外 `NVJPEG_BACKEND_LOSSLESS_JPEG` 走的是 JPEG-LS，最多两通道、只支持预测模式 1。它跟普通 JPEG 不是一回事，别混用。

5. 硬件解码器的边界

硬件后端是 Ampere 之后才有的——A100 上那颗 NVJPG 单元把整个解码流程固化进硅片。它的吞吐远高于通用 kernel，但能力被裁得很死：

只支持 baseline 和单 scan。只支持 1 或 3 通道。不支持 4:1:1 和 4:1:0 采样。缩放只支持 1/2、1/4、1/8 三档，而且只有硬件后端能用。

还有一个容易踩的坑：卡不对就没有硬件单元。A100、A30、Hopper、Ada、Blackwell、Jetson Thor 这一代之后才有；更早的卡即使指定了 `HARDWARE`，也会静默回落到其他路径——代码不报错，只是慢。

所以工程上要两条路都实现，先查能力再分派。`nvjpegDecoderJpegSupported()` 就是干这个的。

顺带说一句编码：硬件编码目前只在 Jetson Thor 上提供，桌面卡走的是 GPU kernel 路径。如果你的场景是「在服务器上批量转码」，别指望有硬件编码器。

6. API 的形状

nvJPEG 的对象分四层。理解了这个结构，它所有接口就都顺了：

nvjpegHandle_t　　　库句柄　　←　线程安全，可共享
　└─ nvjpegJpegState_t　解码状态　←　每个线程一个
　　　├─ pinned buffer　主机端中间结果
　　　├─ device buffer　显存端中间结果
　　　└─ decode params　输出格式、ROI、缩放

最小用法是三步：建句柄和状态、先调 `nvjpegGetImageInfo()` 问尺寸再分配显存、最后 `nvjpegDecode()`。

第二步千万别省。自己按「应该是 640×480」去分配，遇到实际尺寸不同的图就是缓冲区溢出——这是接这个库最常见的崩溃原因。

调用粒度有三种，按场景选：

单张用 `nvjpegDecode`，最简单。成批用 `nvjpegDecodeBatched`，吞吐最高。要高吞吐又想和别的计算重叠，用分阶段的那组：`nvjpegDecodeJpegHost` → `nvjpegDecodeJpegTransferToDevice` → `nvjpegDecodeJpegDevice`——把主机阶段和设备阶段拆开，就能让「下一批的 Huffman 解码」和「这一批的反变换」并行。

7. 性能的四个开关

接完能跑，和接完跑得快，中间隔着四件事。

第一，pinned 内存。输入的 JPEG 比特流必须放页锁定内存。用普通 `malloc` 的页内存，H2D 拷贝会慢一个数量级，前面所有优化全白费。这条最容易被忽略，因为它不报错，只是慢。

第二，批量。后端切换有阈值，批量太小 GPU 根本不启用熵解码。文档里那个数字是 50。

第三，别同步。全程异步加 `cudaStream` 才能重叠；中间插一个 `cudaDeviceSynchronize`，流水线立刻断掉。

第四，输出格式选对。`NVJPEG_OUTPUT_RGB` 是平面格式（三个平面分开），`RGBI` 才是交错格式（RGBRGB…）。选错就是一张错位的花图，而且不报错。pitch 的单位是字节，不是像素——这两个坑常一起出现。

8. 什么时候不该用它

这一段比前面都重要。

小图、单张、低帧率——nvJPEG 往往比 libjpeg-turbo 还慢。

原因很直白：GPU 解码每次都有固定开销，kernel 启动、pinned 缓冲管理、可能的同步。一张 256×256 的图，CPU 解码约 0.1 到 0.2 毫秒，而 GPU 路径光调度就不止这个数。

拿三路 256×256、31 赫兹来算：大约 94 张每秒，CPU 全部解开不到 20 毫秒每秒的 CPU 时间——连一个核的 2% 都不到。

在这个管线上上 nvJPEG，大概率是负优化。

它真正划算的时机只有三种：单张到了一千零八十线，或者批量几十上百；解码结果立刻要在 GPU 上做推理，省掉那趟 H2D；吞吐瓶颈已经确认卡在 JPEG 解码，而不是模型。

先做 profile，再上库。否则你会花三天接完 nvJPEG，最后发现瓶颈在图像缩放。

9. 收尾

nvJPEG 解决的从来不是「怎么解得更清楚」，而是「在哪解、谁来回搬」。它不改变内容，只改变路径。

所以选它之前，先问一个更朴素的问题：这条路上，真正在等的是解码，还是别的什么。
