从哪里进入项目

CODEX DESKTOP

找人 · 角色主会话

在「G2开发项目」里找项目助理，或直接找对应研发角色。主会话常驻，负责收单和分工。

TASK CHAT

跟事 · 一卡一聊天

每张卡关联一个可见的桌面聊天。标题用「卡号｜任务名称｜当前状态」，打开即可读最近简报或继续沟通。

PROJECT BOARD

看全局 · 项目看板

只读看板汇总状态、负责人、交接与登记路径。研发通过工作区工具回写；飞书按配置推送重要变化。

谁负责什么

G2 项目专业项目助理

澄清目标和验收口径，提出拆卡、优先级及里程碑建议。跟踪依赖、风险、证据与归档，向负责人提交进展、选项和建议。

项目负责人及指定验收人

负责人决定优先级、资源取舍和发布安排。卡上指定的验收人按约定条件判断是否通过，并留下结论和依据。

定位开发

负责定位、双目标定、坐标系和观测质量；接口变化时说明数据含义和验证方法。

导航移动开发

负责站位、目标点选择、移动和终态回执；验证定位输入与下游动作之间的约定。

上料开发

负责取放料、配方、带载姿态和执行流程。并行任务分别记录进展、阻塞和结果。

上料可视化开发

维护业务观察台 g2_viewer，展示机器人状态、定位和上料过程。项目任务进度由项目看板展示。

同一个角色怎样并行做两件事

例如，上料角色可以同时接到“分析执行耗时”和“排查取料失败”。每张卡绑定一个桌面可见的聊天，标题带卡号、任务名和状态。用户打开第一张卡看统计口径，打开第二张卡看故障证据。两边都能独立留下待确认项，主会话继续接单。

需要改代码的任务再登记 Git 工作树、分支与基线，开工或恢复前核对卡号、聊天和实际目录。只读排查可以先从日志开始。两棵工作树能隔离未提交的修改，但两张卡依然可能改到同一个接口文件；助理要把重叠路径和集成顺序写到交接里，请接收方确认。

一张卡如何走到归档

  1. 接单与拆卡

    先在 g2.py list 查重，再写清目的、交付物、唯一主责、验收人和完成条件。能独立交付的工作拆成子卡，通过 --parent 关联。项目助理标出先后依赖、资源冲突和需负责人决定的取舍。

  2. 绑定桌面任务聊天

    按卡号查找、创建或复用聊天，将卡号、桌面宿主和聊天 ID 登记到角色的 workers。任务聊天回读卡片，留下首份简报。即使同属上料角色，两张并行卡也各有可见入口。

  3. 登记代码工作树并开工

    需要改代码时，研发为卡登记仓库、工作树、分支、基线和相关 MR。跨仓任务逐仓登记。开工或恢复时执行 execution.py enter 和 check，核对当前聊天和工作树。只读排查可以直接从日志和回执开始。

  4. 迭代、并行与交接

    研发在开始、阻塞、待验收等节点同步卡片、聊天标题和简报，注明可验证成果、阻塞和下一步。写卡前读最新版本，冲突时重读。不同工作树仍可能修改同一文件，项目助理核对重叠路径，协调修改顺序及集成验证。

    接口变化由上游登记 handoff 并通知下游任务聊天；下游用 ack 写明兼容判断、验证结果或阻塞。在看板上出现交接记录后，仍需接收方实际确认。

  5. 提交证据与验收

    研发附上 MR、提交版本、测试日志或原始回执，将卡置为待验收。指定验收人对照完成条件写结论，项目助理用 verify 登记证据核对结果。尚缺实机验证时注明条件、责任人和下一步。

  6. 结项、归档与恢复

    卡验收完成后，任务聊天写结项摘要，核对并释放活动执行绑定（leave）。确认聊天只属于本卡后归档，项目助理复核。角色主会话常驻，证据、分支和聊天映射保留；重开同一卡时恢复原聊天。

工作区文件架构

以下按用途列出主要目录。项目管理边界是这个根目录内已明确接入的项目和任务。

项目工作区 /
AGENTS.md · README.md工作区总约定和运行说明。接单、会话绑定、验收和归档规则从这里查。
roles/五个角色目录。coordination/AGENTS.md 定义项目助理职责，另四个目录分别是 localization、navigation、loading、visualization。
coordination/roles.json角色与桌面聊天的登记表。thread 指向角色主会话，workers 按卡号关联任务聊天。
coordination/g2.py · execution.py前者读写卡片、进展、交接、核验和路径登记，后者校验当前任务会话与实际代码工作树。
coordination/data/g2.sqlite3保存卡片、状态事件、交接回执、工作树登记与执行绑定。看板从工作区记录取数。
coordination/server.py · index.html只读项目看板的服务和页面。同目录的 g2-workspace-board.service 管理服务，feishu_notify.py 负责通知。
repos/按用途保存算法、资产和设计资产的共享 Git 基础仓。开发前读取此目录的 README。
worktrees/任务代码检出位置。新检出按「仓库／卡号-主题」组织；已有任务以卡上登记的实际路径为准。算法与配套资产应分别核对版本。
work/已有任务的辅助工作文件，例如验证和就绪检查脚本。业务代码的工作树位置以登记记录为准。
evidence/按任务号保存交接、测试与验收材料。卡片记录证据位置，便于从结论追溯原始记录。
g2_viewer/运行中的上料观察台目录。可视化开发改动在 worktrees/g2_viewer/ 下登记的任务检出中进行。
docs/g2-project-guide.html团队使用的离线协作指南。新成员可以先从这里了解角色、入口和任务生命周期。
旧任务迁入时要检查什么？

仅处理明确批准迁入的任务。先核对源分支、HEAD、未提交改动、配套资产和证据，再核对工作区内目标检出，更新卡片路径与桌面聊天绑定。接收方在新路径回读确认后继续开发；旧目录清理由负责人单独决定。

交接示例：工装板坐标更新

以下用假设场景说明定位和导航如何并行，以及何时需要等待。

上游 / 定位

说清变化

定位卡拟更新工装板坐标约定。上游给出旧、新坐标系，资产版本、样例输入和预期输出，指明受影响的导航卡。

下游 / 导航

验证后回执

导航可先用样例准备目标点测试。拿到指定版本后，检查选点和朝向，用结果确认兼容；有偏差则写清复现条件并标记阻塞。

项目助理 / 负责人

解决优先级冲突

项目助理核对两卡是否修改同一资产，跟进回执与复测窗口。若仅有一个实机时段，整理先测哪张卡、对交付的影响和建议，由负责人决定。

汇报时看四项：当前在做什么、哪些结果能复核、还在等谁或什么条件、下一步由谁推进。读者可从卡片找到任务聊天、实际检出和证据。
