多Agent协作在G2开发中的应用

“根据工装板选目标点”听起来是一张导航卡。真正开工时，导航要问定位拿哪一版板模型，还要问上料怎样判断车已停稳。三个 Agent 都回了消息，项目负责人仍有一个问题：这项功能到底推进到了哪一步？

一次导航任务的三方交接

卡片快照 · 进行中　2026 年 11 月 25 日回读任务卡、桌面聊天和接手记录时，这项任务已经迁入统一工作区。下面是前一晚的四条实际记录，时间均为北京时间。

  1. 23:20导航确认从哪里继续开发

    接手方对齐工作树、分支和上游提交，检查聊天与代码目录的绑定，并核对迁移证据的文件校验值。后续开发有了唯一入口。

  2. 23:22上料确认配置兼容，留下联调项

    取料步骤和导航配置可以衔接。一次取料成功、导航到位和最终停车能否通过任务 ID 串成同一次执行，仍要用回执验证。

  3. 23:26定位指出缺少哪个输入

    新工装板模型和 CAD 配准依赖另一张定位卡交付。导航还要核对观测的采集时间和地图版本，才能判断目标点使用了哪一次观测。

  4. 23:27项目助理登记迁移验收结果

    接手检查通过，三方回执齐全。原有离线回归记录已随任务迁入，本轮没有重跑。业务卡保留在“进行中”。

这几条记录给出了下一轮分工：导航排查持续集成中的检查和构建失败，定位补齐模型与配准，上料参与回执联调。仅看“迁移通过”四个字，很容易把功能可用性估高。

谁收单，谁对结果负责

团队设有定位、导航移动、上料、上料可视化四个研发角色，各有一个常驻主会话。用户可以直接找角色，也可以把复杂需求交给项目助理拆解。两种入口都先按任务查重，明确交付物、唯一主责和验收条件，再开任务聊天。

项目助理跟踪依赖，核对证据和潜在文件冲突。研发主责负责技术实现和故障归因，指定验收人判断是否满足条件。涉及优先级、发布或共享实机时段时，助理列出可选安排和影响，由项目负责人拍板。

同一个角色怎样并行做两件事

例如，上料角色可以同时接到“分析执行耗时”和“排查取料失败”。每张卡绑定一个桌面可见的聊天，标题带卡号、任务名和状态。用户打开第一张卡看统计口径，打开第二张卡看故障证据。两边都能独立留下待确认项，主会话继续接单。

需要改代码的任务再登记 Git 工作树、分支与基线，开工或恢复前核对卡号、聊天和实际目录。只读排查可以先从日志开始。两棵工作树能隔离未提交的修改，但两张卡依然可能改到同一个接口文件；助理要把重叠路径和集成顺序写到交接里，请接收方确认。

聊天、代码和证据分别放在哪里

规则与入口 · roles/ 和 coordination/
前者记录角色职责。后者保存角色与聊天的映射、任务卡、事件、交接及工作树登记。只读看板汇总这些记录，看板上的交接仍须通知接收方并收到回执。
开发检出 · repos/ 和 worktrees/
基础仓提供分支与提交，任务工作树承载具体改动。同一张卡跨算法与资产仓时，分别登记两边的版本，才能复现组合。
辅助脚本与证据 · work/ 和 evidence/
任务辅助脚本与验收材料按卡归放。卡片引用可复查的提交、测试或原始回执，聊天记录本轮做了什么、还差什么。

从建卡走到归档

  1. 建卡并绑定。写明交付物、主责与验收人，按卡号创建或复用桌面任务聊天。
  2. 开工与交接。登记检出，核对执行入口。上游说明接口变化、受影响版本和验证方法，下游回写兼容结论或具体阻塞。
  3. 提交与验收。研发附上对应版本的证据，将卡转为待验收。指定验收人逐项核对；缺少实机或生产输入验证时，写明条件与下一步。
  4. 完成与恢复。验收通过后留下结项摘要，释放执行绑定，归档本卡的任务聊天。角色主会话常驻，后续重开同一卡时可恢复原聊天，沿证据继续。

回到选目标点的例子，负责人可以从一张卡回答三个具体问题：导航接手的是哪份代码，定位承诺交付哪份模型，上料还缺哪条停车回执。下一次汇报只要更新这些答案，以及能复核它们的证据。
