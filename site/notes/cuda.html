CUDA 与算子

GPU 快的不是每个核，而是同一时刻有几千份活正在飞。CUDA 把这件硬件事实，抽象成了网格、线程块和共享内存。

1. CUDA 是什么

它不是一个语言，是三层东西叠在一起的平台。

第一层是硬件：一块由许多 SM（流式多处理器）组成的芯片，每个 SM 里有几十到上百个执行单元，外接几 GB 到几十 GB 的显存。

第二层是编程模型：C/C++ 的扩展。你写一个标了 __global__ 的函数，用 <<<blocks, threads>>> 启动它，NVIDIA 的编译器把它编译成能在 GPU 上跑的机器码，运行时负责把它塞进硬件。

第三层是生态：cuBLAS、cuDNN、TensorRT、nvJPEG 这些库，以及 PyTorch、TensorFlow 底下那一整层。绝大多数人不会直接写 kernel，而是通过这一层间接使用 GPU。

三层的分工是：硬件提供并行度，模型让你能描述并行，生态把常见的并行模式提前写好。

2. 为什么快：不是核快，是在飞的活多

先看一个常被忽略的事实：GPU 的单核比 CPU 慢。它的频率更低，没有乱序执行，没有复杂的分支预测，缓存也小得多。

它赢在另一个维度。

CPU 有几十个核，每个核都在拼命把单条指令的延迟压到最低：预测分支、重排指令、预取数据。它擅长「一件事尽快做完」。

GPU 有几千个线程位置。它的策略完全相反：不打算让任何一条指令变快，而是让很多条指令同时在飞。

这里有个关键机制叫延迟隐藏。访问一次显存要等四五百个周期，如果只有一个线程在跑，这段等待就是纯浪费。但一个 SM 上同时驻留着几十个 warp，第一个 warp 卡在等数据，调度器立刻切到第二个、第三个——等第一个的数据回来，它已经等了几十个 warp 的时间，看上去「不卡」。

所以 GPU 的加速不是把 1 秒变成 0.01 秒，而是把原本互相等待的时间填满。这也决定了它的前提：任务必须能拆成大量互不依赖的小工作。拆不开，几千个线程位置就是空的。

3. 执行模型：网格、线程块、warp

CUDA 用三层结构描述并行。

网格（grid）：一次 kernel 启动对应的全部线程。

线程块（block）：网格切成若干块，块与块之间可以完全独立地调度到不同的 SM 上，没有先后顺序保证。

warp：硬件真正的执行单位，32 个线程一组。同一个 warp 里的 32 个线程执行同一条指令，只是数据不同——这叫 SIMT。如果它们在一个条件分支里走了不同路径，硬件会把两条路径串行各跑一遍，这叫 warp 分歧，是性能杀手。

块内可以用 __syncthreads() 做屏障同步，块之间不行（除非用协作组）。这个限制决定了算法的组织方式：凡是需要全局同步的步骤，就得拆成多个 kernel 或者两阶段完成。

4. 内存层次：性能真正的战场

如果只记住一句，就是这句：GPU 上的算子快不快，几乎全看它怎么用内存。

看图 4。寄存器一个周期，共享内存三十个周期，L2 两百个周期，显存五百个周期——差了三个数量级。

于是所有高性能 kernel 都遵循同一个套路：把要重复使用的数据搬到离计算单元最近的地方，算完再走。

还有一个容易被忽略的细节：合并访存。当一个 warp 的 32 个线程访问连续的一段地址时，硬件会把它们合并成一次内存事务；如果它们东一个西一个，就要发 32 次。同样的字节数，带宽差一个数量级。

所以写 kernel 的第一原则不是「怎么算得快」，而是「怎么让 32 个线程一次把数据拿回来」。

5. 加速怎么发生：以矩阵乘法为例

矩阵乘法是最好用的例子，因为它有明确的「复用」可以榨。

朴素写法是三重循环：每个输出元素 C[i][j]，都要读 A 的一整行和 B 的一整列。N×N 的矩阵算下来，全局内存要读 2N³ 次。

但同一行 A 被 N 个输出元素共用，同一列 B 也被 N 个输出元素共用。这些复用全被浪费了。

分块（tiling）的做法是：把 C 切成若干 T×T 的块，算一块的时候，把 A 的对应行面板和 B 的列面板先搬到共享内存，然后块内所有线程反复用它。

这样每个面板只从显存读一次，被复用 T 次。全局访问从 2N³ 降到 2N³/T——计算量一点没变，省掉的全是重复读。

6. 算子是什么

这个词在两个语境里指两件东西，很容易混。

在深度学习框架里，算子是一个数学操作：矩阵乘、卷积、softmax、LayerNorm、ReLU。它是计算图上的一个节点，有输入张量、输出张量和形状推导规则。你写 torch.matmul，用的就是这样一个算子。

在 CUDA 里，算子最终落成一个或多个 kernel——也就是真正在 GPU 上跑的那些函数。

两者的关系是：一个算子可以有多种实现，框架在运行时挑一个给你。同一个卷积，可能走 cuDNN 的某个融合 kernel，也可能走手写的特化版本，还可能走编译器生成的。挑哪个，取决于形状、数据类型、显存布局，甚至当时哪块缓存是热的。

所以「算子性能」其实是两层：算法层面选了什么分解方式，和实现层面访存组织得好不好。

7. 算子怎么工作：四个决定

不管什么算子，写出来都要回答四个问题。

第一，怎么切分。把输出张量切成块，每个线程块负责一块。GEMM 是两级分块（块级、线程级），卷积是先把输出按空间切块，再在内层展开成矩阵乘。

第二，怎么访存。块内要复用的数据放进共享内存；相邻线程访问相邻地址，保证合并；必要时做向量化读取，一次取 128 位而不是 32 位。

第三，怎么映射线程。哪个维度对应 threadIdx.x，哪个对应 threadIdx.y。映射方式直接决定了访存是否连续——这是最容易写错、也最影响性能的一步。

第四，怎么处理边界。当形状不是块大小的整数倍时，多出来的线程要早退，又不能破坏同步。这是 kernel 里一半的 if 语句的来源。

拿 softmax 举例，它比 GEMM 更能说明问题。softmax 要减去最大值再取指数求和，天然是两趟：第一趟求最大值和和，第二趟才能归一化。对一行做没问题，但如果一整行放不进一个线程块，就得拆成跨块归约——两个 kernel，中间落一次显存。后来有人把两趟合成一趟（在线 softmax），代价是要边算边修正，这就是 flash attention 那类工作的起点。

再往上一层是融合：把几个算子合成一个 kernel，省掉中间结果写回显存再读出来的往返。在带宽受限的模型里，这一步的收益往往比把单个算子优化 10% 更大。

8. 案例：把 softmax 从三趟压成一趟

前面讲的都是结构。这一节拿一个具体的算子走一遍，看那四条决定落到代码里是什么样子。

选 softmax，因为它几乎出现在每个注意力头里，而且它的瓶颈特别典型：算得很少，搬得很多。

定义很熟：

softmax(x)ᵢ = exp(xᵢ − max) / Σⱼ exp(xⱼ − max)

减 max 是为了数值稳定。exp 增长太快，输入只要到几十就会溢出成 inf，减掉最大值能把指数控制在 1 以内，结果不变。

朴素写法：一行数据走三遍

写成 kernel，最自然的拆法是三个 pass：

第一遍读完这一行，求最大值。第二遍再读一遍，算 exp(x−max) 并累加求和。第三遍读回来做除法。

一行数据被读三次、写两次（第二遍写出指数，第三遍写出结果），搬运量是 5 倍数据大小。

而它算了多少次？每个元素大概三次浮点运算：减、取指、加。按 4 字节数据算，算术强度不到 1 FLOP/Byte——远低于 GPU 的算力带宽比。这意味着不管算力多强，这个算子都快不起来：它卡在带宽上，不在算力上。

在线写法：一趟算出 max 和 sum

能不能只读一遍就把最大值和指数和都拿到？可以，代价是维护两个累加量：

m ← max(m, xᵢ)
l ← l · exp(m_old − m_new) + exp(xᵢ − m_new)

关键在那个 exp(m_old − m_new)。当新的最大值出现时，之前累加的和对「新基准」来说偏大，必须整体缩一次；没有新最大值时这个因子等于 1，乘了也不变。

下面可以把这六个数走一遍。注意第二次和第三次都触发了重标定。

走完一遍拿到 (m, l)，第二趟用 exp(xᵢ−m)/l 写出结果。总搬运从 5 倍降到 3 倍——读两遍、写一遍。算术一点没变，省的全是带宽。

这个技巧在哪儿用

注意力机制里，softmax 作用在一个 N×N 的分数矩阵上。标准做法是：算完整个矩阵、对它做 softmax、再乘 V。那个 N×N 矩阵必须落显存，序列一长就爆。

flash attention 做的事情，正是把上面这个在线技巧搬进分块循环：每处理一块 K 和 V，就用 running max 和 running sum 去重标定已经累加的输出，永远不落地整个分数矩阵。换句话说，它不是在注意力上做了个新算法，而是把 softmax 的在线写法推广到了 attention 的分块结构里。

这也是为什么这一类工作的收益常常是几倍而不是几个百分点：它们省的是显存往返，而不是算术。

9. 两版代码

前面那四条决定落到代码上，大概就是下面这些行。用一个线程块处理一行，块内 256 个线程。

先解决每个块都要用的归约

求和、求最大值这类操作，每个线程先算自己那份，再在块内合并。合并用共享内存两两对折，比原子操作快得多：

// 块内归约：共享内存上两两合并，直到只剩一个值
__device__ float block_max(float v, float* s) {
    s[threadIdx.x] = v;
    __syncthreads();
    for (int off = blockDim.x >> 1; off > 0; off >>= 1) {
        if (threadIdx.x < off)
            s[threadIdx.x] = fmaxf(s[threadIdx.x], s[threadIdx.x + off]);
        __syncthreads();               // 每一轮都要同步
    }
    return s[0];
}

__device__ float block_sum(float v, float* s) {
    s[threadIdx.x] = v;
    __syncthreads();
    for (int off = blockDim.x >> 1; off > 0; off >>= 1) {
        if (threadIdx.x < off)
            s[threadIdx.x] += s[threadIdx.x + off];
        __syncthreads();
    }
    return s[0];
}

两个循环里的 __syncthreads() 不能省。每一轮都有一半线程读取另一半刚写下的值，没有屏障就会读到上一轮的旧数据。

朴素版：三趟

__global__ void softmax_naive(const float* __restrict__ x,
                              float* __restrict__ y,
                              int rows, int cols) {
    __shared__ float s[1024];
    const int row = blockIdx.x;          // 一个块负责一行
    const int tid = threadIdx.x;
    const float* xr = x + (size_t)row * cols;
    float*       yr = y + (size_t)row * cols;

    // 第一趟：这一行的最大值
    float m = -INFINITY;
    for (int i = tid; i < cols; i += blockDim.x) m = fmaxf(m, xr[i]);
    m = block_max(m, s);
    __syncthreads();                     // 复用 s 之前必须同步

    // 第二趟：算指数，顺手写回 y，同时求和
    float sum = 0.f;
    for (int i = tid; i < cols; i += blockDim.x) {
        const float e = __expf(xr[i] - m);
        yr[i] = e;
        sum += e;
    }
    sum = block_sum(sum, s);
    __syncthreads();

    // 第三趟：读回 y，除以和，再写回
    const float inv = 1.f / sum;
    for (int i = tid; i < cols; i += blockDim.x) yr[i] *= inv;
}

softmax_naive<<<rows, 256>>>(x, y, rows, cols);

三段循环对应三趟显存访问，和前面算的一致。i += blockDim.x 这种写法叫跨步循环：列数不整除线程数时也能覆盖全部元素，而且每次访问都是连续的，正好满足合并访存。

在线版：一趟求 (m, l)，一趟写出

__global__ void softmax_online(const float* __restrict__ x,
                               float* __restrict__ y,
                               int rows, int cols) {
    __shared__ float s[1024];
    const int row = blockIdx.x;
    const int tid = threadIdx.x;
    const float* xr = x + (size_t)row * cols;
    float*       yr = y + (size_t)row * cols;

    // 一趟：每个线程只留下自己那部分的 (m, l)
    float m = -INFINITY, l = 0.f;
    for (int i = tid; i < cols; i += blockDim.x) {
        const float mi = fmaxf(m, xr[i]);
        l = l * __expf(m - mi) + __expf(xr[i] - mi);   // 重标定 + 累加
        m = mi;
    }

    // 线程之间：先合并最大值，再把各自的 l 换到新基准
    const float gm = block_max(m, s);
    __syncthreads();
    const float gl = block_sum(l * __expf(m - gm), s);

    // 第二趟：只剩写出
    const float inv = 1.f / gl;
    for (int i = tid; i < cols; i += blockDim.x)
        yr[i] = __expf(xr[i] - gm) * inv;
}

全篇最关键的是这一行：

gl = block_sum( l * __expf(m - gm), s )

每个线程手里的 l 是按自己的 m 算出来的，基准不一样，不能直接相加。所以要先在块内求出全局最大 gm，再用 exp(m − gm) 把每个线程的 l 缩放到同一个基准上，最后才求和。

这一步和第二节的交互里第 2、3 步触发的是同一个动作，只是从「一个线程内重标定」变成了「线程之间重标定」。我用一组十个数做过数值核对：m = -INFINITY 的线程贡献 exp(−∞) = 0、0 × 0 = 0，不会产生 NaN，最终结果与标准 softmax 逐位一致。

四个容易写错的地方

第一，__syncthreads() 的位置。它必须被块内所有线程执行到。放进 if (tid < off) 里面，或者放进只有部分线程会走的分支，整块会挂死。

第二，复用共享内存前要同步。上面 block_max 返回之后，s[0] 里还留着最大值；紧接着 block_sum 第一行就写 s[threadIdx.x]。中间那个 __syncthreads() 就是为这件事留的。

第三，__expf 是有代价的。它是硬件近似指令，比 expf 快好几倍，但精度大约差两个 ulp。做推理没问题，做需要严格复现的数值实验就别用。

第四，一个块只适合不太长的一行。行有几万列时，一个块吃不满 SM，得拆成两段：第一个 kernel 并行算出每行的 (m, l) 落到显存，第二个 kernel 再读回来归一化。前面说的「块间不能同步」，代价就在这里。

编译很简单，注意指定架构：

nvcc -O3 -arch=sm_80 softmax.cu -o softmax

块大小取 128 到 256 之间比较稳。__shared__ float s[1024] 决定了 blockDim.x 不能超过 1024；再大就要换成动态共享内存或分块。

10. 收尾

回头看，CUDA 没有发明新的数学，也没有让单个核变快。它做了三件事：把并行拆成网格与块，让同一时刻有几千份活在飞；把内存分层，让复用发生在离计算最近的地方；把这两件事抽象成一套可编程的模型。

而算子，就是这套模型在具体问题上的落地。同一个矩阵乘，朴素写法是「算得对」，分块写法是「少读几次」——差别从来不在算术上。
